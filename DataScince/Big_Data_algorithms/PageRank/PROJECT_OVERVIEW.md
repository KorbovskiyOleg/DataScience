# Проект PageRank (mrjob) — разбор по шагам

Документ помогает быстро объяснить преподавателю идею, устройство кода и порядок работы проекта.

## 1. Идея и формат данных
- Цель: вычислить важность узлов ориентированного графа с помощью алгоритма PageRank.
- Модель: каждая страница делит свой ранг поровну между исходящими ссылками; итоговый ранг страницы — сумма вкладов входящих ссылок, скорректированная коэффициентом затухания *d* (обычно 0.85).
- Вход: строки вида `node_id\tout_link1,out_link2,...` (опционально третье поле — текущий ранг). Примеры в `graph.txt`, `graph_simple.txt`, `graph_large.txt`.

## 2. Как запускается алгоритм
- Основной скрипт: `run_pagerank.py`.
- Команда по умолчанию: `python run_pagerank.py` (берёт `graph.txt`, 10 итераций, damping 0.85, пишет `pagerank_results.txt`).
- Параметры: `python run_pagerank.py [input_file] [output_file] [iterations] [damping]`.
- Для одной итерации MapReduce напрямую: `python pagerank.py --damping 0.85 graph.txt`.

## 3. Общий конвейер (`run_pagerank.py`)
1) Печать шапки и статистики (`print_header`, `print_statistics`): считает число узлов и рёбер по входу.  
2) Подготовка первого входа: копирует граф в `temp_pagerank_input.txt`, добавляя ранг 1.0, если он не указан.  
3) Цикл итераций:
   - Собирает команду для `mrjob`: `python pagerank.py --damping d -r inline current_file`.
   - Запускает MapReduce, измеряет время, парсит stdout, фильтрует служебные строки, сохраняет результат итерации в `temp_pagerank_iter_{i}.txt`.
   - Предыдущий временный файл удаляется, новый используется как вход следующей итерации.
4) После последней итерации результат сохраняется под указанным `output_file`.
5) Печать топ-результатов (`print_results`): сортирует по рангу, выводит таблицу и сводку.  
6) Уборка временных файлов (`cleanup_temp_files`).

## 4. Ключевая логика MapReduce (`pagerank.py`)
Используется `MRJob` с одним шагом (`steps` возвращает один `MRStep`).

### Mapper: распределение ранга (`mapper_distribute_rank`)
- Парсит строку `node\tout_links\tcurrent_rank`.
- Сохраняет структуру графа для редьюсера (эмитит `(node, graph_info)`), чтобы не потерять исходящие ссылки между итерациями.
- Делит текущий ранг на число исходящих ссылок и для каждой ссылки эмитит вклад `(target_node, rank_info)`.
- Если исходящих ссылок нет, защита от деления на ноль — считается одна «виртуальная» ссылка (узел удерживает ранг).

### Reducer: сбор и пересчёт (`reducer_collect_rank`)
- Получает для каждого узла набор `graph_info` (со структурой) и несколько `rank_info` (вклады от соседей).
- Суммирует все вклады во входящий ранг `total_incoming_rank`.
- Использует формулу PageRank: `new_rank = (1 - d) + d * total_incoming_rank`, где `d = self.options.damping`.
- Выводит строку `node\tout_links\tnew_rank` — это вход следующей итерации.

### Важные строки и их роль
- `current_rank = float(parts[2]) if ... else 1.0` — подхватывает стартовый ранг или ставит 1.0.
- `rank_per_link = current_rank / num_links` — равномерное распределение ранга.
- `yield node, graph_info` — сохраняет исходящие ссылки, чтобы структура графа не терялась между итерациями.
- `total_incoming_rank += float(value.get('value', 0.0))` — суммирование вкладов всех ссылающихся узлов.
- `new_rank = (1 - damping) + damping * total_incoming_rank` — базовая формула PageRank.

## 5. Логика итераций и сходимость
- Каждая итерация уточняет ранги; типично 10–20 итераций достаточно.
- Damping factor 0.85 предотвращает «залипание» ранга в циклах и имитирует вероятность случайного перехода на произвольную страницу.

1) «Берём граф (узел → список исходящих).»
2) «Инициализируем ранги (1.0).»
3) «На каждой итерации mapper делит ранг узла на его исходящие ссылки и отправляет вклады адресатам; отдельно несёт структуру графа.»
4) «Reducer собирает вклады, суммирует, применяет формулу `(1-d) + d * сумма` и выдаёт новый ранг + исходящие для следующего круга.»

## 9. Парадигма MapReduce — подробное объяснение

### Суть
MapReduce — модель распределённой обработки больших данных, предложенная инженерами Google (Джеффри Дин и Санжай Гемауат, 2004). Идея: разделить вычисления на два универсальных шага — *map* (преобразование и эмиссия пар ключ–значение) и *reduce* (агрегация значений по ключу). В рамках распределённой системы планировщик автоматически раскладывает map-задачи ближе к данным, сортирует/перетасовывает (shuffle) пары, подаёт их на reduce-узлы и обеспечивает отказоустойчивость.

### Где стоит применять
- Огромные объёмы данных, не помещающиеся в память/на один сервер.
- Задачи со сводимыми агрегатами по ключу: подсчёт частот, инвертированные индексы, PageRank, статистика логов, ETL.
- Сценарии, где изоляция задач и простая модель отказоустойчивости важнее латентности.

### Плюсы
- Масштабирование горизонтально: добавление машин даёт прирост производительности.
- Отказоустойчивость: падающие узлы перезапускаются на других машинах, данные дубируются в HDFS/локальных чанках.
- Простая программная модель: два шага (map/reduce) минимизируют когнитивную нагрузку.
- Данные локальны к вычислениям: планировщик старается запускать map рядом с блоками данных.

### Минусы и ограничения
- Высокая латентность: каждая стадия — дисковые записи, сеть, shuffle/sort.
- Неэффективно для итеративных алгоритмов (PageRank, ML): нужно много стадий, данные гоняются между диском и сетью (Spark решает через in-memory RDD/DataFrame).
- Плохо для интерактивных запросов и низких задержек.
- Модель ключ–значение требует «вписывать» алгоритм в map/reduce шаги.

### Эволюция и альтернативы
- Hadoop MapReduce (Yahoo! и open-source сообщество) — доминировал для batch-обработки на кластерах.
- Apache Spark — in-memory вычисления, DAG вместо цепочек map/reduce, быстрее на итеративных и интерактивных задачах.
- Apache Flink — потоковая и батчевая обработка с низкой латентностью.
- Google Dataflow / Apache Beam — унифицированная модель batch + streaming, переносимость рантаймов.
- Serverless-вычисления (AWS Lambda + S3, Google Cloud Functions) для ad-hoc map/reduce-подобных задач на небольших объёмах.

### mrjob: что даёт библиотека
- Абстракция над Hadoop Streaming для Python: пишем классы `MRJob` с методами `mapper`, `reducer`, `combiner`, `steps`.
- Запуск в разных режимах: локально (`-r inline`), на Hadoop, EMR, Dataproc — без переписывания кода.
- Упрощённый ввод/вывод: парсит stdin/stdout, сериализация/десериализация (по умолчанию JSON), может использовать протоколы.
- Конфиги и опции: удобно передавать параметры (`add_passthrough_arg`), логирование.
- Тестирование: локальный режим позволяет гонять джобы без кластера.

### История применения MapReduce
- Google использовал MapReduce для индексации веба, логов, построения инвертированных индексов, вычисления PageRank на огромных кластерах.
- Hadoop MapReduce (Doug Cutting, Mike Cafarella) воспроизвёл концепцию в open-source, став основой «больших данных» 2010-х.
- Сегодня MapReduce остаётся для крупных batch-задач на существующих Hadoop-кластерах, но новые проекты чаще стартуют на Spark/Flink/Beam из-за скорости и удобства итеративных вычислений.

### Когда выбрать MapReduce сегодня
- Уже есть Hadoop-кластер и пайплайны на нем; нужно дописать совместимый batch-джоб.
- Задача простая, линейная по данным, без сложных DAG и без жёстких требований к латентности.
- Хотите надёжный и проверенный движок для оффлайн-агрегаций, где время выполнения в минуты/часы приемлемо.

### Когда лучше Spark/Flink/Beam
- Итеративные алгоритмы (ML, графы), где in-memory кэширование резко ускоряет работу.
- Потоковая обработка, низкие задержки, интерактивные запросы.
- Сложные DAG, где много стадий и нужно планирование зависимостей без промежуточных дисковых этапов.

### Кратко про вклад Дина и Гемауата
- Статья «MapReduce: Simplified Data Processing on Large Clusters» (OSDI’04) описала модель, автоматическую оркестрацию, fault tolerance, и показала, что многие задачи (в т.ч. PageRank) сводятся к паре функций.
- Этот подход позволил разработчикам писать простые функции, а управление распределённым исполнением (шардирование, повтор, балансировка, локальность данных) передать фреймворку.
